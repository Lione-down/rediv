# Revid UI Impeccable Audit & Polish 计划

## 1. 目标

先对 `ui/` 下现有原型做一次可执行的审计，找出会影响整体完成度的问题，再把这些问题收敛成后续 `Impeccable polish` 的打磨顺序、验收标准和边界。

本文件只基于当前源码与现有设计文档，不依赖过时截图。

## 2. 审计范围

- `ui/index.html`
- `ui/revid-prototype.html`
- `ui/revid-space.html`
- `ui/design-direction.md`
- `ui/revid-ui-design-plan.md`
- `ui/revid-requirements-status.md`

## 3. 审计结论

当前原型的问题，不是单点小瑕疵，而是「视觉系统不够统一，信息层级不够收敛，页面职责有点散」。

更具体地说：

- 首页、工作流页、个人空间页各自的视觉表达还没有完全收进同一套系统里。
- 画布页的辅助面板、提示、底部工具和右侧属性栏都在抢注意力，主视觉中心不够绝对。
- 移动端虽然能用，但还是偏“桌面缩小版”，不是一套真正优先级重排过的移动布局。
- 文案、卡片、按钮、节点、状态块之间的语气不完全一致，容易出现“像原型集合，不像产品”的感觉。

## 4. 主要问题清单

### 4.1 视觉系统不统一

问题：

- `index.html` 偏首页壳，`revid-prototype.html` 偏工作流壳，`revid-space.html` 又是另一套内容壳，三者虽然都用了深色和玻璃感，但层级、阴影、圆角、按钮密度并不完全一致。
- 同一项目内存在不同的按钮半径、面板厚度、阴影强度和辅助文字语气。
- 品牌锚点不够强，页面虽然不丑，但辨识度还不够集中。

影响：

- 用户会感觉“这是几个页面拼起来的”，不是一个完整产品。
- 后续 polish 时容易每页单独微调，越调越散。

改进方向：

- 先定一套全局 token，再统一每页的 surface、radius、shadow、border 和 spacing。
- 首页、工作流页、个人空间页都要遵守同一套“轻边界、强层级、弱装饰”的规则。

### 4.2 首页信息架构偏散

问题：

- 首页除了主入口，还塞了创作链路、最近项目、TV Show、个人中心下拉等内容。
- 首屏虽然信息丰富，但主任务不够单一，容易分散用户注意力。
- 入口很多，但真正最重要的动作没有被压到绝对第一位。

影响：

- 首页更像产品展示页，不像“进入工作流的操作起点”。
- 用户第一次进入时，路径会比预期更长。

改进方向：

- 首页只保留 1 个主动作，1 个次动作，1 个最近项目区块。
- 其他内容改成折叠区或次级入口，不和主 CTA 抢视觉。

### 4.3 工作流页的视觉重心还不够绝对

问题：

- 画布、右侧属性栏、底部 dock、快捷提示、minimap、浮层短语都在占视觉资源。
- 节点是主角，但辅助 UI 的存在感仍然偏高。
- 一些辅助 chip 和提示条过多，导致“原型感”比“产品感”更强。

影响：

- 用户会先扫到很多控制区，再回头找画布。
- 画布虽然很大，但第一眼不一定是唯一焦点。

改进方向：

- 把画布定为绝对主角，其他区域都降噪。
- 减少同级别卡片数量，改成“默认隐藏，交互时浮出”的进阶信息。
- 让非主流程信息尽量靠边，避免平铺。

### 4.4 右侧面板信息密度过高

问题：

- 资产、模板、属性、危险操作都堆在一个长面板里。
- 面板内部层级虽然完整，但首屏会显得比较重。
- 对于未选中节点状态，很多内容并不是当前最需要的。

影响：

- 面板像“管理后台设置页”，不像“创作时的上下文面板”。
- 用户会在不需要的时候看到太多内容。

改进方向：

- 用状态驱动的渐进披露，默认只露最必要的当前节点信息。
- 资产、模板、属性拆成明确的任务区，而不是全量展开。
- 危险操作必须更弱化，且固定在底部，不参与首屏竞争。

### 4.5 移动端仍偏桌面压缩版

问题：

- 目前移动端更多是把桌面结构改成纵向堆叠，但优先级重排还不够彻底。
- 底部 dock、快捷键提示、节点卡片和辅助区块容易挤在一起。
- 小屏下个别信息块看起来像“为了保留而保留”，不是为移动场景重新设计。

影响：

- 375px 宽度下的阅读和操作负担仍然偏高。
- 主要任务没有得到足够强化。

改进方向：

- 移动端要优先保留画布和主要动作，次级区域折叠。
- 关键按钮要压缩成底部单条操作带，减少横向占用。
- 先做“能顺畅完成任务”，再做“完整展示”。

### 4.6 文案和状态语气不完全一致

问题：

- 页面中既有“产品化短语”，也有“说明书式长句”，还有一些偏原型占位的语气。
- 不同页面的提示文案密度不一致。
- 按钮、标签、状态词的表达颗粒度不统一。

影响：

- 产品感被稀释，原型感会被放大。
- 用户更难形成稳定预期。

改进方向：

- 所有页面统一成“简短、明确、可执行”的语气。
- 强操作用动词，状态用名词，解释只保留必要信息。
- 让文案先服务于动作，再服务于解释。

## 5. Impeccable Polish 原则

1. 先统一系统，再做局部美化。
2. 先压缩辅助信息，再抬高主任务。
3. 先做布局收口，再做视觉抛光。
4. 先修移动端优先级，再修细节。
5. 先解决看起来像原型的问题，再考虑更细的质感。

## 6. Polishing 顺序

### Phase 1, 统一基线

- [x] 统一全局颜色、圆角、阴影、边框和 spacing。
- [x] 统一按钮、chip、卡片、面板的状态规范。
- [x] 统一三页的基础视觉语言。

### Phase 2, 收敛信息架构

- [x] 首页减少并列区块。
- [x] 工作流页减少同层级辅助控件。
- [x] 右侧面板做渐进披露。

### Phase 3, 强化主视觉中心

- [x] 首页的主 CTA 更明确。
- [x] 工作流页的 canvas 更像唯一主舞台。
- [x] 个人空间页更聚焦内容管理，不抢主流程视觉。

### Phase 4, 移动端重排

- [x] 重新定义 375px 优先布局。
- [x] 把高频操作沉到底部或折叠区。
- [x] 确保不横向溢出，不互相遮挡。

### Phase 5, 最终打磨

- [x] 清理冗余说明文案。
- [x] 统一 hover、active、selected、empty、loading、danger 状态。
- [x] 做一轮全页复核，保证三页在同一产品语境里。

## 7. 验收标准

- 首页一眼能看出主入口，不会像内容门户。
- 工作流页一眼能看出 canvas 是主角。
- 右侧面板不会压过主流程。
- 375px 宽度下不出现严重拥挤、遮挡或横向溢出。
- 三个页面的视觉语气、按钮体系、卡片语气一致。
- 用户能明显感到这是一个完成度更高的产品，而不是原型拼接。

## 8. 后续执行方式

后续如果继续做 `Impeccable polish`，建议按下面顺序推进：

1. 先补 token 和共享样式基线。
2. 再收首页和工作流页的首屏层级。
3. 再清右侧面板和底部 dock。
4. 最后做移动端与文案收尾。

每一轮 polish 完成后，都要把本文件里的对应 Phase 标记为完成，并把新增发现同步回进度文档。
